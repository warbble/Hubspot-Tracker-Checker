# Railway Migration Design

**Date:** 2026-06-30
**Status:** Approved

## Goal

Move the HubSpot Tracking Code Checker off Vercel and onto Railway. The app keeps its
exact user-facing behavior; only the hosting platform and the rate-limit backend change.

## Background

Today the app is two pieces wired together by Vercel conventions:

- `public/index.html` — static front end, served at `/` by Vercel.
- `api/check.js` — a Vercel serverless function (`export default async function handler(req, res)`)
  invoked per request at `POST /api/check`. It renders the target site via Browserless.io,
  detects HubSpot tracking, upserts a HubSpot CRM Company/Contact, and rate-limits callers
  using Vercel KV (Upstash Redis over its REST API).

Vercel supplies three things the code leans on: static file serving, per-request function
invocation, and the KV REST endpoint. Railway runs a long-lived container instead, so the
migration replaces those three with a single Node web server plus a Railway Redis service.

## Approach

**Express + ioredis, single web service** (chosen over a native-`http` no-framework build and
over a two-service static+API split). Express serves the static front end and the one API
route from one process; ioredis talks to a Railway Redis service over TCP. The existing
handler logic ports over almost verbatim because Vercel's `req.body` and `res.status().json()`
match Express's shapes.

## Railway Topology

One Railway project, two services:

- **Web service** — this repository. Built by Nixpacks (auto-detected Node), started with
  `npm start`, listening on Railway's injected `$PORT`. Public domain generated by Railway.
- **Redis service** — Railway's Redis. The web service references it via `REDIS_URL`.

## Code Structure

### Add: `server.js`
Express application and process entry point:
- `express.json()` body parsing (replaces Vercel's automatic body parsing).
- CORS headers (ported from the handler) and an `OPTIONS` preflight short-circuit.
- `express.static('public')` — serves `index.html` at `/` and any future static assets.
- `app.post('/api/check', handler)` — mounts the ported handler.
- `app.listen(process.env.PORT)` — binds the Railway-injected port.

### Add: `lib/rateLimit.js`
The one component that must change. Exports `checkRateLimit(ip)`; backed by a single shared
ioredis client constructed from `REDIS_URL`. Behavior (unchanged policy):
- Key `rate:<ip>:<YYYY-MM-DD>`, limit 2 per IP per day.
- `INCR` the key; if the result is `1`, `EXPIRE` it to 86400s. Deny when the count exceeds 2.
- **Fails open:** if `REDIS_URL` is unset or any Redis call throws, allow the request
  (`{ allowed: true, remaining: 999 }`) — matching today's behavior.
- Using `INCR` + conditional `EXPIRE` is atomic and fixes a latent read-then-write race in the
  current GET-then-SETEX implementation.

### Edit: `api/check.js`
- Remove `export const config = { maxDuration: 30 }` (no Vercel function config on Railway;
  Railway imposes no per-request timeout, so the Browserless latency workaround is unneeded).
- Remove the inline `checkRateLimit` (moved to `lib/rateLimit.js`) and import it instead.
- Keep all tracking-detection logic (`checkHubSpotTracking`, `analyzeTracking`) and all HubSpot
  CRM logic (`saveToHubSpot` and helpers) as-is.
- Export the handler so `server.js` can mount it. The handler still reads
  `req.headers['x-forwarded-for']` for the client IP — Railway sets this on proxied requests.

### Edit: `package.json`
- Add `"type": "module"` so the existing ESM syntax runs on plain Node.
- Add dependencies: `express`, `ioredis`.
- Scripts: `"start": "node server.js"`; remove the `vercel` `dev`/`deploy` scripts.
- Keep `"engines": { "node": ">=18" }`.

### Remove
- `vercel.json`, `.vercel/`, `api/.gitignore`.

### Untouched
- `public/index.html` — posts to `/api/check` on a relative path, which still resolves against
  the same origin. No change needed.

## Environment Variables

| Variable | Source on Railway | Notes |
|----------|-------------------|-------|
| `BROWSERLESS_TOKEN` | Set manually | Required; carried over from Vercel |
| `HUBSPOT_TOKEN` | Set manually | Required for CRM save; carried over |
| `DEBUG_KEY` | Set manually (optional) | Bypasses rate limiting when passed as `debug` |
| `REDIS_URL` | Referenced from the Redis service | Replaces `KV_REST_API_URL` / `KV_REST_API_TOKEN` |
| `PORT` | Injected by Railway | Server must bind to it |

Dropped: `KV_REST_API_URL`, `KV_REST_API_TOKEN`, and the other `KV_*` / Upstash vars.

## Provision & Deploy

Performed via Railway tooling, confirming before outward-facing steps:

1. Create (or select) the Railway project.
2. Add a Redis service.
3. Create the web service from this repo; wire `REDIS_URL` to the Redis service.
4. Set `BROWSERLESS_TOKEN`, `HUBSPOT_TOKEN`, and (optionally) `DEBUG_KEY`.
5. Deploy (`railway up`), generate a domain, and verify with the README's test URLs
   (`hubspot.com` → positive, `wikipedia.org` → negative).

## Out of Scope

- No change to detection heuristics, HubSpot property schema, or front-end behavior.
- No GitHub-based Railway deploy pipeline (using `railway up` from the CLI); can be added later.
- The booking link / front-end copy is unchanged by this migration.

## Local Development

`railway run npm start` injects the Railway service env vars (including `REDIS_URL`) into a
local run, replacing the old `vercel dev` + `vercel env pull` flow.
